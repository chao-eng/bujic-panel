# PRD：导航卡片交互、站点品牌化与多导航 Tab 增强

> 需求来源：5 条前端体验类 Issue（#1 卡片不展示网址 / #2 hover 不破坏布局 + 操作改菜单 / #4 顶部导航 Tab 支持自定义多个 / #5a 站点 title·logo 自定义 / #5b 内外网自动跳转）。
> 范围外：#3 自定义配色——因涉及主题系统重构，单独立项（见附录 A）。
> 状态：评审完成，待排期。版本 v1.1 / 日期 2026-09-07。
>
> v1.1 变更：R4 由「双视图改语义化命名」升级为「导航 Tab 可配置多个」。Tab = 顶层导航容器，内含分组；每个 Tab 整体绑定一种渲染形态（卡片/列表），分组只归属一个 Tab，其渲染形态由所属 Tab 决定。

## 0. 原始需求基线（追溯表）

| 需求编号 | 原始诉求 | 拆解后的产品含义 |
|---------|---------|----------------|
| R1 | 卡片不要展示网址，展示不全、拥挤 | 卡片常态 = 图标+名称；网址/描述移入悬浮提示与菜单信息，不落卡片文案 |

## 1. 产品概述

### 1.1 产品背景
Bujic Panel 为高颜值、自托管、多用户的网站导航与书签管理系统，核心用户为 NAS / 家庭内网 / 私有云部署者。当前导航卡片 hover 时重排内容、卡片直接展示完整网址，站点名/图标无法自定义，且顶部被固定为「收藏 / 书签」两种不可编辑的视图，用户不理解二者差异、也无法按自己的信息架构组织导航。内网地址字段 `lanUrl` 已在数据层存在但无 UI 与跳转逻辑。

### 1.2 第一性原则分析
> 回到本质：导航面板在用户“高频扫一眼 → 点一下跳走”这个瞬间，真正提供的是什么？

1. **本质需求**：低干扰、低认知负担地把用户带到目标页面；导航结构是“我的”，可随个人信息架构自由组织。
2. **必要条件**：
   - 卡片信息密度收敛（图标+短名即可，长文本交给提示）。
   - hover 反馈只用来“确认我可点”，不做内容迁移，避免视觉噪声。
   - 管理操作（编辑/删除/排序）不挤占浏览版面，收进菜单。
   - 顶层导航 = 用户自定义的一组 Tab；Tab 承载同形态分组，形态（卡片/列表）不再是与分组并列的“另一种模式”。
   - 站点名称/图标属于“这个面板是我的”，须可配置。
   - NAS 用户常在内外网间切换，点击应自动命中可达的地址。
3. **约束**：
   - 浏览器无法读取客户端本机私网 IP → 内外网判定只能走服务端来源 IP。
   - 判定必须“静默完成一次”，不可进入点击跳转的同步链路。
   - 数据结构演进（新增 Tab 实体）需兼容现有存量库（无迁移基础设施，走轻量升级回填）。
   - 多用户：每位用户的导航结构（Tab→分组→书签）彼此独立，Tab 归属用户而非全局。

### 1.3 产品目标（可测）
| 指标 | 度量口径 | 目标 |
|------|---------|------|
| 卡片视觉噪声 | 常态卡片视觉元素数量 | 常态 ≤ 2 类主元素；操作入口不再常态可见 |
| hover 布局稳定度 | hover 前后 DOM 布局是否位移 | 0 位移（仅 border/底色/光晕变化） |
| 导航结构自组织 | 用户能否自行增删改 Tab、移动分组跨 Tab | 全部可操作且所见即所得 |
| 站点品牌化 | 登录页 / 浏览器标签 / 首页顶栏是否随全局配置联动 | 三处全部跟随 |
| 内网命中率 | 内网环境点击填有 `lanUrl` 的书签命中 `lanUrl` 的比例 | ≥ 99% |

### 1.4 数据模型核心抽象（R4）
```
User（现有，1 用户 N 导航）
  └─ ViewTab（新增，userId 归属）     ← 顶层导航 Tab
       ├─ name: 展示名（如「工作」「NAS 工具」）
       ├─ type: 渲染形态 = card | list   ← 整体绑定一种形态
       ├─ sort: 排序
       └─ 含 N 个 ItemIconGroup
            └─ ItemIconGroup.tabId（新增，替代原 groupType 的界面过滤职责）
                 └─ 含 N 个 ItemIcon / 监控 Widget
```
- **Tab 与分组**：一对多；一个分组只属于一个 Tab；删除 Tab 默认级联删除其下分组与书签（二次确认）。
- **形态与分组解耦**：分组的渲染形态不再由自身 `groupType` 决定，而由所属 Tab 的 `type` 决定；同一形态可同时存在多个 Tab。
- **遗留 `groupType` 列**：改为弃用（不再用于 UI 过滤），仅存量数据升级时读一次用于回填 `tabId`，随后不写不读（保留列避免大改表）。

## 4. 详细交互设计

### 4.1 页面整体交互流程
```
登录 → 首页
  ├─ 加载：服务端下发 站点品牌 + 我的 Tab 列表 + isLan（一次缓存）
  ├─ 顶部 Tab 条：Tab1 | Tab2 | ⋯ | [+ 新建] [⋯管理]
  ├─ 主体：激活 Tab 的分组区
  │    ├─ Tab.type=card → 卡片网格；=list → 信息流列表
  │    ├─ 分组：hover 可折叠；卡片 hover 轻反馈
  │    ├─ 卡片：点主体→跳转；点⋯/右键→操作菜单
  └─ 设置 → 外观：站点品牌 / 网络区域(管理员)
```

### 4.2 Tab 条交互（新增）
- 顶部原「模式切换胶囊」替换为可横向滚动的 **Tab 条**。
- 项：名称 + 激活高亮 + 关闭按钮（hover 出现）；条尾常驻「+」与「管理（⋯）」。
- 管理弹窗 `TabManageModal`：列表可拖拽排序；每行支持改名/改形态（select）/删除；顶部「新建 Tab」输入名称+形态。
- 切换记忆 key：`bujic-active-tab`（localStorage）。

### 4.3 内外网跳转时序图
```
  浏览器                     Next 服务端                    目标站点
    │ 1. GET / (登录态)          │                              │
    │ ─────────────────────────▶│ 2. X-Forwarded-For/socket     │
    │                           │ 3. lan_subnets 比对 isLan     │
    │ 4. {tabs, brand, isLan}   │                              │
    │ ◀─────────────────────────│                              │
    │ 5. 缓存 isLan                                             │
    │ 6. 点卡片 (lanUrl 非空)                                    │
    │    isLan ? 归一并开 lanUrl : 开 url                        │
    │ 7. window.open/a.click                                   │
    │ ────────────────────────────────────────────────────────▶│
```

**lanUrl 归一化规则（BR-14 落地）**
- 无 scheme（如 `192.168.31.202:8096`）自动补 `http://`。
- 解析后仅 `host[:port]` → 拼接 `url` 的 pathname/search。
- 无法解析则忽略 `lanUrl` 回退 `url`。
- Widget 书签不启用 `lanUrl`（BR-17）。

### 4.4 关键迁移流（R4 存量库升级）
```
存量库：ItemIconGroup.groupType = website|webpage，无 view_tab 表
   │  start.js / 升级脚本 检测：view_tab 空 且 存在 group 行
   ▼
   ┌─ 对每个 user：
   │    ├─ 若存在 groupType='website' 的组 → 建 Tab「收藏」(type=card)
   │    ├─ 若存在 groupType='webpage' 的组 → 建 Tab「书签」(type=list)
   │    ├─ 组.tabId = 所属形态对应的 Tab
   │    └─ 若用户无任何分组：只建一个默认 Tab「常用」(type=card)
   ▼
   新结构就绪；groupType 列不再读写
```

## 6. 非功能需求

### 6.1 性能
- Tab 列表随首屏一并下发，切换为本地过滤（BR-11）；`isLan`、品牌、Tab 数据同一批下发，无额外往返。
- 点击跳转链路零新增请求（BR-15）。hover 过渡限 border/底色。

### 6.2 兼容性
- 近两个大版本浏览器；触摸设备依赖「⋯」/Tab「+」入口。
- Tab 条溢出可横向滚动；长 Tab 名截断。

### 6.3 安全与隐私
- `lan_subnets`/来源 IP 属网络拓扑信息，仅管理员可见；判定端点不额外暴露 IP。
- 站点图标沿用 `/uploads` 穿越防护；品牌配置不落日志。

### 6.4 可靠性
- 判定失败静默回退 `url`（BR-16）；品牌/Tab 配置损坏回退默认（BR-28）。
- 存量库升级必须幂等：重复运行升级脚本不产生重复 Tab / 重复迁移（见 §4.4 幂等检查）。

### 6.5 技术验证清单
| 项 | 说明 | 排期前 Spike |
|----|------|-------------|
| 服务端取客户端 IP | Docker 直连 vs Nginx `X-Forwarded-For` 的可靠性 | 确认部署拓扑与 header |
| 右键+拖拽共存 | `onContextMenu` 与 PointerSensor 互斥 | 原型验证 |
| metadata 动态化 | App Router 动态 `title/icons` 的缓存行为 | 验证 fetch 时机 |
| Tab 迁移幂等 | 升级脚本检测 view_tab 空 + group 行存在 + 已迁移标记 | 确认唯一检测键 |

## 7. 附录

### A. 范围外：#3 自定义配色（单独立项）
- 现状：主题 = CSS 变量 + 大量 `[data-theme$="-light"]` !important 覆写（`globals.css`），组件大面积 `text-white/xx`。
- 结论：直接开放任意填色会在浅色主题下脏色/对比度崩坏；需先引入语义 token 白名单（默认文字/高亮文字/主色/页面底色/卡片底色/悬浮底色/选中底色/边框色）再支持自定义持久化。建议本次 PRD 后独立排期。

### B. 术语表
| 术语 | 含义 |
|------|------|
| 导航 Tab | 顶层导航容器，绑定一种渲染形态 card/list，内含若干分组 |
| 渲染形态 | card（卡片网格）/ list（信息流列表），由 Tab 决定 |
